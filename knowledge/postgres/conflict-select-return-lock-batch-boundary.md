# DO SELECT の返却・lock・batch 境界

## 問いと結論

get-or-create で「なければ挿入、あれば既存 ID を返す」を一文にまとめたい。PostgreSQL 19 の `ON CONFLICT DO SELECT` はこの用途を直接表現するが、**返却成功、新規作成、後続処理までの排他、batch 内の一意性は別の契約**である。特に `FOR UPDATE` の追加は待機だけでなく、同一文で新しく挿入した行への重複 input の成否も変えうる。

既存の [RETURNING OLD の監査差分](returning-old-concurrent-trigger-boundary.md) は 18.6 の修正、[分離レベルと再試行](transaction-isolation-retry.md) は transaction 全体を扱う。本書は 19 移行時の insert-or-get と batch API に絞る。完成済みの idempotency service や exactly-once 処理方式ではない。

以下は公式契約、固定ソースの静的観察、そこからの独自設計案を区別する。PostgreSQL runtime は実行していない。

## 1. 返った一行は「今作った一行」とは限らない

[19 INSERT manual](https://www.postgresql.org/docs/19/sql-insert.html)および RC1 同梱文書で確認した契約は次のとおり。

- `conflict_target` と `RETURNING` は必須。選択対象は指定した arbiter の競合行であり、他の独立した制約エラーまで成功へ変換しない。
- conflict で DO SELECT に進むと既存行を返す。入力 payload への更新は行わず、返却用の OLD / NEW は同じ既存値になる。
- conflict の `WHERE` が true でなければその行は返らない。locking 付きでは、返却から除外された競合行も lock される。
- command tag の count は挿入・更新・返却選択された行数。新規 INSERT 件数や distinct key 件数として集計しない。

次は独自の未実行 SQL 例。base table の id は PRIMARY KEY かつ GENERATED BY DEFAULT AS IDENTITY とし、省略時に ID が生成される前提とする。tenant_id と item_key は NOT NULL、両列には UNIQUE があり、RETURNING の意味を書き換える rule 等はない。PRIMARY KEY だけでは省略した id が自動採番されないことに注意する。

```sql
INSERT INTO item AS i (tenant_id, item_key, payload)
VALUES ($1, $2, $3)
ON CONFLICT (tenant_id, item_key) DO SELECT
RETURNING id, payload, (old.id IS NULL) AS inserted;
```

既存行の id は非 NULL なので、`old.id IS NULL` をこの前提下の作成判定に使える。nullable な任意列で判定しない。返された payload は送信した $3 と同じとは限らないため、同じ key で異なる要求を誤って同一視しない。

独自設計として payload 一致を `DO SELECT WHERE i.payload = excluded.payload` で要求する場合、これは conflict branch の条件であり、競合しない新規 INSERT の入力検証ではない。空の RETURNING を「key が存在しないから別経路で作り直す」と解釈しない。BEFORE INSERT の抑止等もあるため、空結果の原因が payload 不一致だけだとも決めつけない。

## 2. READ COMMITTED の insert-or-get と通常 SELECT の snapshot は違う

[19 isolation manual](https://www.postgresql.org/docs/19/transaction-iso.html)は、READ COMMITTED の DO SELECT が未確定の競合 transaction を待ち、その transaction が commit した競合行を返せることを説明する。statement 開始時の snapshot に見えなかった行でも返る。これは未commit値を返す dirty read の許可ではない。WHERE での除外や独立したエラーがない対象についての契約として読む。

一方、通常の SELECT は statement 開始時の snapshot を読む。[WITH manual](https://www.postgresql.org/docs/19/queries-with.html)でも、data-modifying CTE と親 query は同じ snapshot を使う。

この二つから導く独自の反例は、旧式の `DO NOTHING RETURNING` CTE と同一文内の通常 SELECT を UNION するだけでは、「競合時も必ず ID が返る」とは保証できないこと。T1 が key を未commitで挿入し、T2 がその前の snapshot で文を開始して競合待ちし、T1 が commit すると、T2 の INSERT は DO NOTHING となる一方、通常 SELECT は T1 の行を見られず、両 branch が空になりうる。これは資料の契約から組み立てた実行順の分析であり、本調査で再現した観測ではない。

RC1 の [ExecOnConflictSelect / ExecCheckTupleVisible](https://github.com/postgres/postgres/blob/0b8bff042a997fe50fcd1c4c83b9ef1cc9ed8a89/src/backend/executor/nodeModifyTable.c)には、transaction snapshot が必要な分離レベルで visibility を検査し、別 transaction の不可視行との競合なら serialization failure にする経路がある。READ COMMITTED の結果保証を REPEATABLE READ / SERIALIZABLE に移植して retry を削除しない。transaction 全体の再試行方針は既存文書を参照する。

## 3. row を返すことと後続処理まで保持することは別

RC1 の [isolation spec](https://github.com/postgres/postgres/blob/0b8bff042a997fe50fcd1c4c83b9ef1cc9ed8a89/src/test/isolation/specs/insert-conflict-do-select.spec)と [expected output](https://github.com/postgres/postgres/blob/0b8bff042a997fe50fcd1c4c83b9ef1cc9ed8a89/src/test/isolation/expected/insert-conflict-do-select.out)を静的に確認した。

- 既存 row に対する lock 指定なしの二つの DO SELECT は、先行 transaction の COMMIT 前に双方が返る。
- 双方が DO SELECT FOR UPDATE なら後続が待機し、先行の COMMIT または ABORT 後に進む。
- この fixture は事前に存在する row の READ COMMITTED 試験であり、あらゆる競合で nonblocking になることを証明しない。unique check などの待機は別にある。

[locking manual](https://www.postgresql.org/docs/19/explicit-locking.html)上、row lock は transaction 終了または対応 savepoint rollback で解放される。したがって、後続 UPDATE と同じ transaction に入れず、autocommit の get-or-create だけに FOR UPDATE を付けても、次の文までの予約にはならない。

FOR KEY SHARE は key 変更や DELETE を防ぐ一方、非key列の UPDATE は防がない。payload を不変のまま利用したい用途で「何かの lock があれば同じ」と扱わない。また、FOR UPDATE は row を lock するため disk write を起こしうる。DO SELECT を無条件に read-only・zero-write と広告しない。

独自設計上の判断は、ID 取得だけなら不要な強い lock を避け、同じ transaction 内で値を使って変更するなら必要な lock 強度・待機上限・deadlock retry を決めること。性能改善量は測定していない。

## 4. FOR UPDATE の追加で batch の成否まで変わる

RC1 の [insert_conflict.sql](https://github.com/postgres/postgres/blob/0b8bff042a997fe50fcd1c4c83b9ef1cc9ed8a89/src/test/regress/sql/insert_conflict.sql)と [expected output](https://github.com/postgres/postgres/blob/0b8bff042a997fe50fcd1c4c83b9ef1cc9ed8a89/src/test/regress/expected/insert_conflict.out)の selfconflict 節には、次の版固定の差がある。

- 同じ文で未登録の key を二度提案する lock なし DO SELECT は、最初に作られた値を二回返す。READ COMMITTED / REPEATABLE READ / SERIALIZABLE の各 fixture にこの期待出力がある。
- 対応する DO SELECT FOR UPDATE は、同一文で新しく挿入した row を再び対象にして cardinality violation になる。これを「事前に存在する同じ row への繰返しは常に失敗する」という一般則へ拡張しない。

[executor](https://github.com/postgres/postgres/blob/0b8bff042a997fe50fcd1c4c83b9ef1cc9ed8a89/src/backend/executor/nodeModifyTable.c)の静的観察では、lock なしの経路は row version を取得し、locking 経路は ExecOnConflictLockRow を通る。後者は TM_Invisible かつ自 transaction 由来の row に ERRCODE_CARDINALITY_VIOLATION を出す。単に SELECT と UPDATE の返却値が同じかどうかでは、この分岐差を説明できない。

独自設計として、batch input を arbiter の同値性に合わせて正規化・重複排除し、同じ key で異なる payload を渡す場合の採用／拒否規則を先に決める。返却配列の件数を新規作成数と同一視せず、元 input への対応付けも定義する。FOR UPDATE への変更時は、待機時間の回帰試験に加え、同一batch内重複の回帰試験を必須にする。

## 5. 「既存行を更新しない」は「副作用がない」ではない

RC1 [ExecInsert](https://github.com/postgres/postgres/blob/0b8bff042a997fe50fcd1c4c83b9ef1cc9ed8a89/src/backend/executor/nodeModifyTable.c)は conflict 判定より前に BEFORE ROW INSERT trigger を呼ぶ。trigger が挿入候補を書き換えたり、挿入自体を抑止したりできる。[trigger expected output](https://github.com/postgres/postgres/blob/0b8bff042a997fe50fcd1c4c83b9ef1cc9ed8a89/src/test/regress/expected/triggers.out)でも DO SELECT の候補に BEFORE INSERT が走り、書換え後の key で既存値が返る例を確認した。upstream の期待出力を読んだのであって、今回そのテストを実行したわけではない。

[sequence manual](https://www.postgresql.org/docs/19/functions-sequence.html)は、ON CONFLICT の競合検出前に必要な nextval を含む候補行が計算されると説明する。既存 row を返しただけでも採番が進みうるため、gapless sequence や採番回数による作成数の推定は成立しない。

独自設計として、既存行を返すためだけの擬似的な DO UPDATE を置換できても、transaction を越える外部処理の重複排除、通信断時の初回 commit 判定、削除後の同一 key 再作成まで自動解決すると考えない。必要な副作用は idempotency key・記録の保存期間・業務 transaction の境界を別に設計する。

## 未実行の runtime 試験案と限界

採用予定の server build と driver で、少なくとも以下を検証する。

1. 新規・既存・異なる payload・WHERE false/NULL で、返却値、空結果、inserted 判定を区別する。
2. 未commitの INSERT に対する競合待ちを、先行 COMMIT / ROLLBACK の両方で確認する。CTE fallback と DO SELECT を比較する。
3. 同じ key の batch を lock なし／FOR UPDATE で比較し、新規 key と事前存在 key を分ける。
4. lock 取得後の後続文を同一 transaction と autocommit で比較し、別sessionの UPDATE / DELETE がいつ進むか確認する。
5. 高い分離レベルの serialization failure と transaction 全体の retry、BEFORE INSERT の抑止・書換え、sequence 増分を確認する。
6. 実運用 role で必要な権限を確認する。INSERT manual は DO SELECT の SELECT 権限、locking 付きでは少なくとも一列の UPDATE 権限も要求する。RLS / view / partition / FDW の全組合せは未検証であり、この例の base table 前提をそのまま拡張しない。

本書の確認は文書・固定ソース・upstream期待値の読解までで、性能測定、ローカル PostgreSQL 実行、ORM 互換性、GA 後の再確認は未実施。検索 eval は記事を取得できるかの検査であり、SQL の正しさを実行検証するものではない。
